Recording is optional and independent of the actor/grader. `recorder.js` uses Web Audio capture/PCM encoding, requesting 24 kHz mono, with a muted monitor. Stop and page exit release microphone tracks.

The server accepts canonical mono, 16-bit PCM WAV at supported sample rates (8, 16, 22.05, 24, 44.1, or 48 kHz), validates actual structure/length/duration, and ignores client duration claims. Limits: **120 seconds per clip, ten clips per attempt, 11,520,044 bytes maximum WAV payload**; the request gate permits bounded multipart overhead. Private files use random UUID names with 0600 permissions under a 0700 directory, outside static assets.

Only the owning learner can add audio to an active, unexpired attempt. Invited/active trainer/admin and that learner may play it through authenticated object checks. New audio after submission/expiry is denied. A repeated identical upload acknowledges the existing clip without duplication, including retry after closure if that stored file still exists; a missing file does not masquerade as success. Failed storage/DB writes clean up and return bounded errors without private details.

Save requires explicit JSON confirmation with a recording ID, not merely HTTP 200. A redirect to sign-in must not erase the preview. Save timeout is 20 seconds; failure/lost acknowledgment preserves the preview, and retry deduplicates. Re-login in a separate tab can refresh CSRF while the first tab retains its audio. A second recording cannot silently overwrite an unsaved preview. Page lifecycle/back-forward recovery resets controls; a navigation warning protects unsaved work where supported. **Unsaved audio is browser memory, not durable storage; closing/leaving can lose it.**

## 10. Security, limits, and failure behavior

- Loopback-only middleware and allowed-host checks; `DEBUG=False`. Do not widen the bind address, proxy this publicly, or treat the local configuration as production-ready.
- Magic links expire after ten minutes, are single-use, browser-bound through the issuance session, and need a CSRF-protected confirmation POST. GET/HEAD/scanner visits do not sign in or consume them. Tokens travel in the URL fragment and only their digest is stored. Issuance is limited to five links per user per 15 minutes and only reserved demo identities.
- Session cookie is HTTP-only with Strict same-site behavior, an hour lifetime, and browser-session expiry. CSRF uses a distinct Strict same-site cookie. The signing key is in-memory only.
- Responses are `no-store`. Same-origin CSP covers scripts/styles/network requests; media permits self/blob. Frames are blocked. Inputs are validated and templates escape text.
- Microphone permission is scoped to successful learner attempt pages. Camera and display capture stay blocked throughout. Missing/revoked profiles, other learners, anonymous users, and staff write attempts are denied according to role/object rules.
- Default practice limits: ten inbound/follow-up starts per UTC day, 20 minutes per attempt, 24 selected turns, bounded 100-event transcript/evidence history. Inbound and follow-up each have a one-active-per-assignment constraint. New attempts snapshot configurable session limits; daily-start checks apply the current allowance.
- Stale revisions prevent double actions/overwrites. Conflicting lesson, CRM, callback, and invalid review forms retain reviewable draft text. Interrupted/expired/submitted attempts preserve evidence; retry does not reuse an old attempt ID.
- `PROVIDER_SPEND_LIMIT_CENTS=0`, local scripted voice, preview-only email, and no external clients. Current synthetic usage must have zero estimate and zero reported cost by database constraint. A missing future provider report must remain unknown, not be interpreted as zero.
- The admin view exposes a $50 target and 80% warning default plus manual non-AI operating costs. It does not implement a live spending cap, concurrent cost reservation, provider billing synchronization, or permission to spend.

The zero-provider boundary and single-thread local runtime reduce today's scope. Before any broader use, production auth, transport, secrets, retention, isolation and concurrent behavior require explicit design and verification; none should be claimed from this local test suite alone.
